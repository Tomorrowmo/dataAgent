## 一句话结论

- **具备条件了吗?** —— DataAgent 这一款**具备了**:产品在跑、反馈通道已上线、管理员收件箱已上线、专家可立即开用。另两款(Mirror / Rsight)**产品在跑,但应用内反馈通道还没埋**,先用"人肉通道"覆盖。
- **怎么反馈?** —— 已交付"应用内一键标记 + 管理员收件箱",**带上下文、分三类**;配合"录屏观察 + 三问 debrief"的人肉流程。
- **能沉淀领域知识吗?** —— **已有三个落地槽**(解析器 / 算法 / 流程模板)在沉淀"可执行知识";"判断类知识"这一槽还缺,但**反馈表已作为它的种子**埋下,后续长成"候选→评审→晋升"的纠偏回路。

## 背景:这三个问题为什么是同一件事

我们的北极星不是"做一个更聪明的 AI",而是做一个**容器**——把专家的经验,变成非专家也能信任使用的能力。要让这个容器转起来,需要**冷启动燃料 = 一个真人的经验**。

这次找的这位 CFD + 流程业务专家,就是那桶燃料。所以"让他用、收他的反馈、沉淀成能力"本质是一条链:

```
专家使用  →  暴露摩擦/纠正/判断  →  捕获(带上下文)  →  评审  →  晋升为可执行、可验证、可继承的工件  →  下一个(非专家)用户免费继承
```

一个关键判断(此前已被证伪验证):**飞轮的复发燃料是产品自己反复犯的错,不是凭空"收集领域洞察"。** 所以所有捕获手段都锚定在**失败点和纠正点**,而不是"请专家来录入知识"。

## 问题二:用了之后怎么反馈?

### 设计原则(决定了下面所有实现)

1. **两层反馈,别只搭一层**
   - **Layer 1 产品反馈**:哪不好用 / 做不到 / 不敢信 → 用来修工具。专家会主动说。
   - **Layer 2 专家心法**:他**凭什么**这么判断 → 沉淀成给非专家的能力(= 护城河)。专家**不会主动说**,必须主动追问"为什么"。
2. **对 N=1 的专家,带宽 > 工具**:不先建门户/管线,最高保真是"坐在旁边看 + 低摩擦随手记"。
3. **捕获的扳机是失败和纠正,不是成功**:解析失败、列选错被改、阈值被改、结果被否——这些摩擦点才是知识涌出处。
4. **反馈必须带上下文**:"某处很乱"没用;"在 run #482、数据集 X 上他把列改成电压"才可行动。
5. **三类反馈分桶,别倒进一个大桶**:能力缺口 / 正确性 / 信任,去的是三个不同的修复去处。

### 已交付的手段

#### A. 应用内「一键标记 / 反馈」按钮(DataAgent)
- 文件:`web/components/FeedbackButton.tsx`,挂载于 `web/app/app/page.tsx`,全工作台任意页面常驻右下角。
- 专家在**想法发生的当下**点一下,选一类、写一句、`⌘/Ctrl+Enter` 发送。
- 自动带上上下文:当前视图 `view`、会话 `conversation_id`、数据集 `dataset_id`、运行 `run_id`、页面 URL、UA、客户端时间。
- 四个分类(对应三个落地槽 + 兜底):
  - `cannot` 想做但做不到 → 能力缺口
  - `wrong` 它做错了 → 正确性 / 真值
  - `distrust` 不敢信结果 → 信任 / 解释·验证 UX
  - `idea` 想法 / 其它

#### B. 管理员「反馈收件箱」(DataAgent)
- 文件:`web/components/FeedbackInbox.tsx`,侧栏入口在 `web/components/Sidebar.tsx`(仅 `is_admin` 可见),渲染于 `web/app/app/page.tsx`。
- 能力:按**状态**(待处理 / 已查看 / 已完成)和**类型**筛选并计数;每条卡片显示类型徽章 + 内容 + 上下文小标签(view / conv# / dataset# / run# / 打开页面↗);一键在 `new → triaged → done` 之间流转(乐观更新)。
- 权限:管理员看全部,普通用户(专家)只看自己的——既能让老板集中分流,又不暴露互相的反馈。

#### C. 后端接口与存储
- 模型:`backend/app/db/models.py` 新增 `Feedback` 表。字段:`kind` / `text` / `view` / `conversation_id` / `dataset_id` / `run_id` / `context(JSON)` / `status` / `created_at`。
  - 上下文 id **故意不加外键**:被引用的会话/数据集以后被删了,反馈(及它当时指向 id N 的事实)也必须留存。
- 路由:`backend/app/api/feedback.py`,挂载于 `backend/app/main.py`:
  - `POST /api/feedback` 提交
  - `GET /api/feedback` 列表(管理员全量 / 普通用户仅自己)
  - `PATCH /api/feedback/{id}` 改状态或重分类
- 前端封装:`web/lib/api.ts` 的 `submitFeedback` / `listFeedback` / `updateFeedback`。

#### D. 配套的人肉流程(覆盖三款产品,零开发)
- **看他用**:录屏 + 出声思考,你闭嘴只看——重点抓"沉默放弃"(他不会上报、但最值钱的失败信号)。
- **吐槽群**:一个微信/飞书群,随手丢原话,你来分类。比任何表单都低摩擦。
- **用完三问**(对应三个落地槽)+ 一句 Layer 2:
  1. 哪一步你**想做但做不到**?
  2. 哪一步它**做错了你得手动改**?
  3. 哪一步你**不敢信它的结果**?
  4. (Layer 2)"你刚那个判断,脑子里在比对什么?"

## 问题三:咱们的系统能沉淀领域知识吗?

### 先定义"沉淀/落地"
知识落地 **≠** 写进文档/wiki/笔记。在这个可验证 agent 里,只有变成**可执行 + 已验证 + 下一个人免费继承**的工件,才算落地。三个硬条件缺一不可:
- **可执行**:是代码/规则/参数,不是一段话
- **已验证**:过了信任门(trust gate)——破工件会污染池子,门是必须的
- **可继承**:下一个用户什么都不用知道,自动吃到

### 已经在沉淀的(三个落地槽,已存在)

| 知识类型 | 落地槽(表/机制) | 状态 |
|---|---|---|
| 文件格式怎么读 | `format_adapters`(教一次,以后自动解析) | ✅ 黄金标准:用户只想打开文件,系统顺手留下解析器 |
| 用什么算法/方法 | `algorithms`(user/ai 来源,`is_verified`、`test_report`) | ✅ 有;跨用户继承(`is_public`)路径已留待激活 |
| 分析流程怎么走 | `flow_templates`(对话流程→可复用模板) | ✅ 有 |

这三槽合起来,等于把"用户让 agent 做了什么、跑了什么、对不对"沉成了**可执行、可验证**的资产。

### 还缺的一槽:判断 / 语义 / 经验
最值钱的领域知识(`电压`这列其实是 voltage、SOC 阈值多少算异常、什么样的结果"看着对"、某个工步怎么切)目前**没有家**,散落在对话里。这正是「渊 / sim-knowledge」那套已经跑通的东西:`_candidates.yaml`(自动攒)→ 真人评审 → `criteria.yaml`(护城河)。

### 这次埋下的种子
本次新增的 `Feedback` 表,就是这一槽的**种子**:
- 专家的每次纠正/吐槽,落库时带 `kind` 分桶 + 上下文 → 天然就是"候选知识(candidate)"。
- 收件箱的 `status`(new→triaged→done)就是评审动作的雏形。
- 攒出量后,顺着 `kind` + `status`,直接长成 **candidate → review → promote** 的纠偏回路:
  - `wrong`(列选错/做错)→ 晋升为**映射规则 / 真值**
  - `cannot`(做不到)→ 晋升为**新算法 / 新流程模板**
  - `distrust`(不敢信)→ 晋升为**解释 / 验证 UX 改进**
- 晋升时过信任门 + 打开 `is_public`,实现"别人的失败 → 专家一次纠正 → 全员永久受益"。

### 结论
**能,而且已经在沉淀**(格式/算法/流程三槽)。差的是"判断类知识"这一槽和跨用户自动继承的激活;反馈系统已把通往它的**第一块砖**铺好。
