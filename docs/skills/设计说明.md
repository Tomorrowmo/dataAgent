# 技能包机制:设计说明

> 面向维护者。用户视角的写法见《[技能包接入规范](技能包接入规范.md)》。

## 1. 要解决的问题

产品原本只有两种"能力":内置算法(可信、少)和 AI 现写的算法(多、不稳)。两者都只是
**一个函数**。而用户真正的资产不是函数,是**一整套做法**:什么数据才够判、按什么顺序做、
用什么判据下结论、结论里必须说清哪些不确定性。这些东西没有地方放,只能靠每次对话重复交代。

技能包就是这个位置:**知识 + 执行体,一起装进来,被 AI 当成高于自身默认习惯的指令**。

风洞质检模块其实是这套东西的第一个实例(判据、报告口径、专用工具都硬编码在
`app/windtunnel/` 里)。技能包把同样的形态开放出去,让用户自己造第二个、第三个。

## 2. 三层披露(为什么不是把文档全塞进提示词)

| 层 | 内容 | 何时进上下文 | 成本 |
| --- | --- | --- | --- |
| 1 | 包名 / description / when_to_use / 工具一句话 | 每轮都在 | 每个包 ~3 行 |
| 2 | SKILL.md 正文 | AI 调 `read_skill` 时 | 一次 ≤16k 字符 |
| 3 | `references/*.md` | 正文指过去、且真的追问时 | 按需 |

装 20 个包,常驻成本仍是几十行。这直接决定了这套机制能不能规模化 —— 全量注入的方案在
第 3 个包就会开始挤占数据上下文。

关键实现:`skills/store.py::prompt_block`(第 1 层)、`chat_agent` 的 `read_skill` 动作
(第 2/3 层)、`store.trigger_hits`(用户原话命中触发词时,额外提示 AI 去看)。

## 3. 工具怎么和现有体系合流

技能包的工具**不另开一套**:`store.tool_index()` 把它们变成和内置算法同形的条目,
进同一张 "Available tools" 表,`run_tool` 用同一个动作调用。

`_execute_action` 里的查找顺序:**内置注册表 → 技能包 → 用户/AI 算法表**。
技能包排在 AI 生成的算法之前 —— 用户亲手写的方法优先于模型现编的。

slug 形如 `battery-health.capacity_fade`。`resolve_tool` 容忍模型常犯的近似写法
(裸工具名、`__` 分隔、大小写),和内置注册表的 alias 表是同一个自愈思路。

## 4. 执行:一个新的沙箱模式

技能包是**磁盘上的多文件代码**,不是一段字符串,所以 `runner_worker` 增加了 `mode="skill"`:
把包根目录挂到 `sys.path`,`importlib` 导入 `entry_module`,取 `entry_func` 调用。
`probe=True` 只导入不调用 —— 安装时用它证明入口真的存在。

隔离仍靠原来那套:独立子进程、墙钟超时、`socket` 连接被封、POSIX 上加 rlimit。

## 4.5 通用 skill 包:零改造接入

网上流通的 skill 包是**给有 shell 的编码 agent 写的**:SKILL.md 里直接写"运行
`scripts/xxx.py --foo`"。本系统的 AI 没有 shell,所以最初的方案(让用户补一份 skill.yaml、
把函数改成 `run(df, **params)`)等于要求用户改别人的包 —— 那不叫支持通用包。

现在的做法是给这类包自动配一把钥匙:

- `manifest.discover_scripts()` 找出包里像"命令"的 .py(在 `scripts/`、`bin/` 下,或带
  `__main__`/argparse);
- 没有 tools 声明时自动合成一个 `run_script` 工具(runtime=`script`,参数 `script` 是包内
  脚本的枚举、`args` 是命令行参数);
- `runtime._run_script()` 按脚本真实的用法执行:跑它、**stdout 原样带回**、把它写出的
  csv/parquet 读回成表格接进流水线;
- 提示词里额外给 AI 一句:这个包让你执行命令时用 `run_script`,**不要假装自己能开终端**。

同时把通用包惯用的写法就地消化掉:`when_to_use` 缺失就从 description 里截"Use when…"那段,
`triggers` 缺失就从名字/描述里挖别名串,`allowed-tools` 等 Claude Code 专有字段原样保留。

trust 因此分成三档而不是两档:`sandbox`(检查过的 python)/ `script`(通用包自带脚本)/
`command`(自带可执行程序)。**script 不并进 command** —— 若把带脚本的包一律设成仅管理员可装,
"通用包直接能用"就成了空话;所以脚本包人人可装、知识立刻可用,只有**真去执行脚本**时才受
服务端开关约束。

## 4.6 参数推荐:不要求用户知道作者的列名

工具的默认参数写的是作者那份数据的列名(`cycle`、`discharge_capacity_ah`),用户手上的数据
可能叫 `Cycle Index`。让用户自己敲对,等于把作者的私有约定摊派给用户。

`skills/suggest.py` 是一个**确定性**匹配器(不调 LLM,打开面板即时出结果,没配 key 也能用):
认出"选列"类参数 → 从这份数据真实的列里按 token 重合度挑最像的 → 说清为什么这么填;
挑不出来时**明说"这份数据不是这个工具要的数据"并列出真实列名**,绝不硬塞一个能跑但没意义的
值 —— 和 agent 那条"列名诚实"是同一条规矩。界面上选列参数直接变成真实列名的下拉框。

顺带修掉一个 UX 硬伤:技能包工具抛的异常信息本来是作者写的人话("数据里没有这些列:…"),
却被沙箱连着 20 行 traceback 一起塞进 error。现在 `_clean_error` 只把人话留在第一屏,
traceback 收进 logs(界面折叠、排查时才展开)。

## 4.7 列映射:三层,只有中间那层能攒下东西

"工具要 `cycle`,这份数据叫 `Cyc_No`"是这类系统绕不开的问题。分三层看,难度和价值完全不同:

| 层 | 做法 | 覆盖 | 代价 |
| --- | --- | --- | --- |
| 字面相似 | token 重合 + 词根/单位后缀剥离(`suggest.score_column`) | 大多数英文变形:`cycle`→`Cycle Index`、`capacity_ah`→`Cap` | 零成本、可解释、**已做** |
| **教过的映射** | 用户指一次 → 一条 `MappingRule`(pattern→role),之后**任何包、任何数据集**都认 | 同物异名、中英混排、厂商私有命名 | 一次人工;**规则默认共享,一人教全员受益** |
| LLM 猜 | 把列名+样本喂给模型让它判断 | 兜底 | 慢、花钱、会自信地猜错 |

关键设计:**参数要声明"我要哪个量"(`role`),而不只是"我要叫 cycle 的列"**。没有这个键,
每个包的私有列名约定各说各话,教一百次也攒不出可复用的东西。`role` 没写时退回用默认列名当
伪 role,所以老包和通用包不受影响。

匹配顺序是 教过的规则 → 字面相似 → **如实说找不到**。第三步不降级去猜:数据里真的没有那个量
时(质量过程数据里没有循环号),任何映射都变不出来,硬指一列只会让结论从根上错。这也是
`teachable` 字段的用途 —— 界面据此给出"指一次"的入口,而不是自作主张。

第三层(LLM 猜)刻意没做:前两层覆盖了绝大多数,而 LLM 在这个位置的错误最隐蔽 —— 它会给你一个
看起来合理、跑得通、结论却错的列。真要加,也必须是"给候选 + 要用户确认",不能直接落参数。

这一层复用的是仓库里早就有的 `MappingRule`(专家判断的沉淀载体)+ `services/mappings.apply_rules`,
技能包这条路以前没接上而已。接上之后规则的 `hit_count` 会累加 —— 存了却从没被读回的知识等于没沉淀。

## 5. 信任模型(这套设计里最需要想清楚的一环)

| | AI 生成的算法 | **技能包(python)** | **通用包(script)** | **技能包(command)** |
| --- | --- | --- | --- | --- |
| import | 白名单(很窄) | 黑名单 + `requires` 放行 | 不检查 | 不检查 |
| `open` | 禁 | 允许(读自己的资产) | 不检查 | 不检查 |
| 隔离 | 子进程 | 子进程 | 子进程 + 只能跑包内 .py + 临时工作目录 | 子进程 |
| 谁能装 | — | 任何用户 | 任何用户(知识立刻可用) | 仅管理员 |
| 谁能**跑** | — | 任何用户 | 需服务端开 `SKILLS_ALLOW_COMMAND_RUNTIME` | 同左 + 管理员安装 |

**只拦"会跑到的代码"**:静态检查从每个工具 `entry` 出发算 import 可达集(动态 import 已被禁,
所以这个集合是完整的);可达文件里的违规拦整包,包里那些没人引用的脚本只提醒。这条是为
"网上下的包"准备的 —— 它们常带另一个运行时的 helper 脚本,让一个永远不会被执行的文件
挡住整包,只会把用户逼向 command runtime 那条真正没约束的路。

**为什么 python 包用黑名单而不是白名单**:白名单会把"用 openpyxl 读个 Excel"这种正当需求
一并拒掉,用户会转而去用 command runtime —— 那才是真正没有约束的路径。黑名单+显式
`requires` 声明,把大多数正当需求留在可检查的路径上。

`command` runtime 存在的理由是现实:用户手里有成熟的求解器后处理脚本、内部 exe,重写代价
高到会让他们放弃接入。所以保留这条路,但把它做成**必须显式打开、仅管理员可装、报告里
明确标注**的形态,而不是假装它安全。

## 6. 安装即验证 + 一句话结论

`build_verdict()` 把六个阶段压成用户真正要的三件事:**能不能装**(硬拦截)、**AI 能拿到什么**
(知识 / 工具 / 两者)、**要改什么**(具体到文件和字段)。安装和 `dry_run` 都返回它,页面上是
那张结论卡。`dry_run` 是"验一下"的后端:全套检查照跑,一个字节都不写。

`installer.install_pack` 的六个阶段(取包 → 读清单 → 静态检查 → 自检运行 → 落盘 → 登记)
每一步都写进 `install_report` 并存进行里,页面上逐条可见。理由和"没有静默步骤"一样:
一个装了却什么都不做的包,比一个明确拒绝的包糟糕得多。

`is_verified` 只在**静态检查全过 + 所有声明的 test 全过**时为真。未通过的包仍可安装
(用户可能只是想先放着),但提示词里会附一句"这个包自检没过,跑不通就如实说" —— 让 AI
不至于对着一个坏工具反复重试。

## 6.5 状态:一个开关,两个只读指示灯

`enabled` 是用户唯一能拨的开关,语义只有一条:**AI 在对话里能不能看到这个包**
(`list_packs(enabled_only=True)` 是唯一入口,提示词块和工具索引都从它派生)。停用不阻止
页面上的手动试跑 —— 排查一个坏包时那正是你需要的路径,但结果里会附一句"这个包已停用,
AI 不会主动用它,本次是你手动触发的",免得看着能跑就以为它在为对话服务。

`is_verified`(自检)和"能否执行脚本"(服务端开关)是**只读指示灯**,不是用户开关。三者正交,
所以详情页用一条三行的状态条一次讲清,而不是让用户在角标之间猜。

一个真实的坑:重装升级原本会把 `enabled` 无条件写成调用方传的值,于是重装一个你亲手停用的包
会把它悄悄放回 AI 面前。现在 `enable=None` 表示"不决定":新装启用、升级保持原状。

## 7. 数据边界

包文件落在 `data/skills/<owner_id>/<slug>/`,按用户隔离;`SkillPack` 行也带 `owner_id`。
读文档、读参考文件一律经 `store._safe_pack_file`,解析后必须仍在包根之下,否则拒绝
(契约测试里有 `../../../../etc/passwd` 这一条)。zip 安装拦目录穿越、符号链接、超大/超多文件。

## 9. 已知的取舍 / 后续

- **只做 python / script / command 三种 runtime**。R / MATLAB 走 command 就够,不专门做;
  通用包里的 .sh/.js 脚本暂不执行(Windows 上多半没解释器,与其运行时炸不如不声称支持)。
- **没有做包之间的依赖**。包与包互不可见,避免出现需要解析的依赖图。
- **触发是关键词匹配**,不是向量检索。装到几十个包以后,这里会变成召回瓶颈,到时再换。
- **没有版本回滚 UI**。升级时旧目录只在安装过程中临时备份,成功即删。真需要回滚,重装旧包。
- **AI 自己"写一个技能包"还没做**。现在只能人写。这是把 `generate_tool` 提升一个层级的
  自然下一步:让 AI 把一次成功的分析沉淀成一个带判据的包,交用户审核后入库。
