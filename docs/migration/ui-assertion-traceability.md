# UI 断言可追溯性映射

> 迁移第 0 阶段产出。回答一个问题：前端重写后，浏览器测试里的每一条断言去哪了。

## 为什么需要这份表

`wt_ui_test.py` 与 `wt_compare_ui_test.py` 驱动真实浏览器，断言绑在 DOM 文本与控件上。前端一旦重写，这两套文件整体作废。

问题不在于文件作废，而在于**没人说得清作废的到底是什么**——是"页面布局对不对"这种可以重做的东西，还是"91837 零飘等于 0.0989"这种代表客户信任的东西。这份表把每一条断言归位，让"能力一个不缺"从一句承诺变成可以逐行核对的事实。

## 结论先说

**46 条浏览器断言里，35 条的领域事实早已在 API 层被独立断言过。**

这推翻了迁移方案初稿里的一个判断。此前认为"客户对齐的数字证据链绑死在 DOM 上、随前端重写作废"——**这是错的**。那三个数字（零飘 0.0989、不回零 0.1002、MZ 载荷占比 28.902%）本来就在 [`wt_api_test.py:169-173`](../../backend/wt_api_test.py) 断言，不经过浏览器。浏览器测试只是把同样的数字再从屏幕上读一遍。

因此前端重写真正失去的，是"这些数字确实被正确显示出来了"这一层确认，而不是数字本身。第 0 阶段的成本因此远低于原估。

| 归类 | 条数 | 含义 |
|---|---:|---|
| 已覆盖 | 35 | 领域事实已在 `wt_api_test` / `wt_matrix_test` 独立断言，与前端无关 |
| 本轮补上 | 3 | 此前只有浏览器断言过，现已下沉到 `wt_contract_test.py` |
| 纯 UI | 8 | 断言的就是布局与交互本身，不可下沉，须在新前端上重新写 |

## 口径校正

清点过程中发现两处文档与代码不一致，一并记录：

- README 记浏览器断言 **27 + 17 = 44** 条，实际代码里是 **29 + 17 = 46** 条（`wt_ui_test.py` 有两处是互斥分支，按执行计 29）。本表以代码为准。
- README 记内置算法 **20** 个，HANDOFF 记 **13 内置 + AI 生成**。此项与风洞无关，留待算法模块迁移时以 `/api/algorithms` 实际清点为准。

## 那 8 条纯 UI 断言

它们不可下沉，因为断言的对象就是界面本身。前端重写后必须在新技术栈上重新写一遍，内容如下：

1. 侧边栏能进入风洞应用
2. 检查完成后切到结果视图并显示明细
3. 判据依据可展开查看
4. 车次选择器紧凑——130 车次时批次汇总仍在首屏（这条来自真实教训：早期按车次卡片平铺，130 车次把所有控件挤出屏幕）
5. 展开车次列表后可搜索、可跳到下一个异常
6. 规则编辑器可打开，阈值可视化编辑不写代码
7. 进入多车次对比视图
8. 筛选结果为累加语义（多次"加入筛选结果"叠加而非替换）

第 4 条值得单独留意：它编码的是一个已经踩过的坑，不是审美偏好。新前端如果不复现这条约束，130 车次的场景会再坏一次。

## 怎么用

迁移期间，任何实现变更后运行：

```sh
cd backend
./.venv/Scripts/python.exe -m uvicorn app.main:app --port 8077   # 另开一个终端
./.venv/Scripts/python.exe wt_contract_test.py
```

`wt_golden.json` 的规矩是**只增不改**。数字若需变更，必须先说明甲方口径变了，而不是新实现算出了别的结果——后者是回归，不是更新。
