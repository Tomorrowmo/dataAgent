# 风洞试验过程质量检查 — 领域应用设计与验收

> 建在 RLab Cortex（DataAgent）平台上的第一个垂直领域应用。
> 入口：登录后左侧导航「风洞质量检查」。

---

## 1. 这个应用解决什么问题

风洞试验一个"车次"（一次吹风）会产出三个文件，试验人员要在下一车次开始前，
判断这一车次的数据能不能用、设备有没有问题，并手写一份「跟班记录」交班。
判据来自十二条工程规则（天平零飘、回零、底压一致性、马赫数一致性…），
过去靠人逐条比对，或靠一套脚本跑出一段自然语言，再靠文本相似度去"猜"它对应哪条规则。

客户已有的演示版本（`FromC/` 下的 Agent1 + Agent2）验证了这条链路可行，
但存在五个使它不能真正上生产的问题。本应用逐条解决：

| 现状问题 | 本应用的做法 |
|---|---|
| 阈值硬编码在 Python 里（`mark1 = 0.005`），改一个限值要改代码 | **规则即数据**：规则存库，试验人员在界面上改区间、改建议语，改完立即生效 |
| 用向量相似度把测量值匹配到规则，出现过「天平零飘 0.0989」被判给「天平回零异常诊断」（匹配度 50.51%） | **特征与规则显式绑定**：规则声明它测的是哪个 feature key，错配在结构上不可能发生 |
| 量纲不自洽：原始 ca 是 MPa，阈值是 mmH2O，脚本直接拿 MPa 数值和 150 比 | 解析层统一换算到 mmH2O（`1 MPa = 101971.62 mmH2O`），阈值与数值同量纲 |
| 天平不在载荷库里就 `IndexError`，被上层吞成「PA 分析失败」 | **未评定是一等状态**：报告如实写"缺什么、怎么补"，绝不静默当成正常 |
| 只有异常检测，没有绘图、没有跨车次趋势、报告不可编辑不可导出 | 补齐气动曲线、多车次趋势、章节可选 + 预览可编辑 + 导出「车次号_跟班记录」 |

在此之上，加了两条客户明确要的**扩展面**：用户能自己加规则，也能让 AI 写新算法。

## 2. 数据与处理链路

```
   ca / pa / da (无扩展名, GBK)
            │  parsers.py     按前缀识别 → 分车次 → 结构化
            ▼
     RunBundle ──────────────────────────────┐
            │  features.py                   │  frames.py
            │  17 个特征算子(只测量,不判定)     │  → 长表 DataFrame
            ▼                                │    (自定义算子的输入契约)
     FeatureValue{value, unit, status}       │
            │  rules.py                      │
            │  规则区间匹配(显式绑定,首命中即止)  │
            ▼                                ▼
        Finding{等级,结论,原因,影响,建议,依据}  沙箱执行的自定义特征算子
            │
            ├─ pipeline.py  多车次编排(零飘跨车次链) + Nelson 趋势判据
            ├─ report.py    质量检查报告 / 跟班记录 / 多车次汇总
            └─ ai.py        分诊 · 规则起草 · 算子生成 · 气动结论 · 结果问答
```

### 三类文件

| 文件 | 内容 | 支撑的检查 |
|---|---|---|
| `ca` | 19×16 数字表，首行初零、末行末零、中间吹风点；压力单位 **MPa** | 零飘、跑码、回零、左右底压、传感器零点、马赫数、总温 |
| `pa` | 分段中文报表：模型/天平参数、CA 回显（kgf/m²）、弹性角、姿态角、气动载荷、标定矩阵 | 底压合理性、底压突变、弹性变形、攻角外插、载荷超量程 |
| `da` | 10×59 气动结果（CAF/CN/CZ/CAB/MX/MY/MZ…）+ 来流条件 | 气动曲线与规律结论、攻角外插的输出网格 |

### 单位约定（`units.py`）

- `1 mmH2O = 9.80665 Pa`（标准重力 CGPM 1901；ISO 80000-4 / NIST SP 811）
- `1 kgf/m² = 1 mmH2O`（精确相等）——这也是 pa 报表能与规则书阈值直接比较的原因
- `MPa → mmH2O`：×101971.62
- 马赫数由总/静压按等熵关系反算：`M = √(5·((p₀/p)^(1/3.5) − 1))`，NACA TR-1135 式(44)

## 3. 规则即数据

一条规则把**一个特征**绑到**一组区间**上：

```json
{
  "rule_id": "rule_01_balance_zero_drift",
  "feature": "balance_zero_drift",
  "applies_when_mach": "",
  "bands": [
    {"level": "critical", "lo": 0.012, "hi": null,
     "verdict": "天平零飘超过 0.012，已超出允许范围",
     "cause": "…", "impact": "…", "action": "建议停止试验并维修天平。"},
    {"level": "warning",  "lo": 0.008, "hi": 0.012, "…": "…"},
    {"level": "notice",   "lo": 0.005, "hi": 0.008, "…": "…"},
    {"level": "ok",       "lo": null,  "hi": 0.005, "verdict": "天平零飘正常"}
  ],
  "refs": ["甲方规则书 …", "AIAA R-091-2003 …"]
}
```

- 区间是半开区间 `[lo, hi)`，按顺序匹配、首命中即止，所以从最严重往下写即可。
- 等级四档：`ok` / `notice`(引起注意) / `warning`(需检查) / `critical`(停止试验)，
  对应报告评级 合格 / 合格(需关注) / 有条件合格 / 不合格。
- `applies_when_mach` 支持分段适用（马赫数一致性在 Ma 2.9 上下容差不同，拆成两条规则）。
- 每条规则都带 `refs`，报告附录逐条列出阈值出处。

### 内置 18 条规则

来自客户 `rules/rule_01…rule_12.md`，并与其 `Application/*.py` 生产脚本逐行核对。
其中两处**规则书与脚本不一致**，未擅自合并，而是在规则的 `note` 里写明并给出取舍理由：

- **rule_04 左右底压**：规则书 150/200/300 mmH2O；脚本用 30/60/100 且数值停留在 MPa
  （换算分支挂在从未取到的 `FD=='2'` 上）。采用规则书数值，在真正的 mmH2O 上比较。
- **rule_05 传感器零点**：规则书第 4 条「差异小于 50 判定正常」与第 1 条「30~50 需注意」
  自相矛盾。采用与脚本一致的 30/50/80 三档，把第 4 条按笔误处理。

客户的 rule_02 把两种物理机理（电源线断 = 跑码**太小**；虚焊/铁屑 = 跳动**太大**）写在一条里，
这里拆成 `rule_02a` / `rule_02b`，各自绑定自己的特征——这正是"测量与判定分离"的意义。

## 4. 两条扩展面

### A. 用户新增异常检测规则

界面「⑤ 知识库 → 规则库」：

1. **手工新增**：选特征 → 填区间 → 写结论/原因/影响/建议 → 保存。全程不写代码。
2. **AI 起草**：一句中文 → 先分诊（现有特征能不能测）→ 生成规则草稿 →
   **在真实车次上试跑**（`POST /wt/rules/preview`，不落库）→ 看到会命中哪些车次 → 确认后保存。

AI 只能在**已存在的 feature key** 里选；选不到就明确回答"需要新增测量量"，
并把请求路由到扩展面 B。它绝不会发明一个不存在的特征，也不会假称阈值来自某个标准
——没有出处时会写「AI 建议值，需人工确认」。

### B. 用户新增分析算法（AI 生成 + 沙箱验证）

一个自定义特征算子就是平台标准的算法模块，输入是本车次的**长表 DataFrame**：

| 列 | 含义 |
|---|---|
| `table` | `ca` / `ca_echo` / `elastic` / `attitude_measured` / `attitude_interp` / `aero_loads` / `da` |
| `point` | `zero_start` / `blow` / `zero_end`（仅 ca 类） |
| `alpha` `variable` `value` `unit` | 攻角、变量名、数值、单位（压力已是 mmH2O） |

```python
META = {"name": "总压波动系数", "slug": "total_pressure_cv", "category": "custom", ...}

def run(df, **params):
    s = df[(df.table == "ca") & (df.point == "blow") & (df.variable == "P0")]["value"]
    if len(s) < 2:
        raise ValueError("吹风点不足 2 个")          # 数据不够就报错，不返回 0 冒充正常
    return {"value": float(s.std(ddof=1) / s.mean() * 100), "unit": "%",
            "detail": f"基于 {len(s)} 个吹风点"}
```

流程：自然语言 → LLM 写码 → **AST 白名单校验**（禁 import os / eval / 文件 / 网络）→
**沙箱子进程执行**（超时 + 内存上限）→ 测试用例必须通过 → 人工审核 → 入算法库 →
规则即可用 `custom:<slug>` 引用它。

选这个契约的原因：它就是平台原有的算法契约，因此自定义算子自动获得沙箱、代码生成自愈重试、
流程模板编排、聊天调用等全部既有能力，而不是另起一套只服务风洞的旁路。

## 5. 报告

三种产物，同一套 findings：

- **质量检查报告**：章节可勾选（概况 / 评级 / 异常明细 / 未评定说明 / 气动曲线 / 多车次趋势 /
  跟班记录正文 / 全部检查项 / 判据附录），预览可直接编辑，导出保留编辑内容。
- **跟班记录**：沿用现行编号叙述格式与 ` - P` 异常标记，命名 `车次号_跟班记录.txt`（UTF-8 BOM，
  Windows 记事本可直接打开）。
- **多车次汇总报告**：各车次评级表 + 趋势 + 问题汇总。

每条异常都写出：监测特征、实测值、判定结论、**原因分析 / 影响评估 / 处理建议**、
计算方法（公式原文）、判据依据。审阅者不用打开源码就能复核一条判定。

### 最关键的一组断言：逐位复现客户生产结果

客户既有工具为 91836~91840 出过跟班记录，本应用独立重算后数值完全一致：

| 项目 | 客户跟班记录 | 本应用 |
|---|---|---|
| 91837 天平零飘 | 0.0989 | 0.098912 |
| 91837 最大不回零量 | 0.1002 | 0.100165 |
| 91837 MZ 载荷占量程 | 28.902% | 28.902% |
| 91837 Q 载荷占量程 | 25.128% | 25.128% |
| 91837 Y 载荷占量程 | 10.112% | 10.112% |
| 五车次评级 | 优秀/不合格(2)/不合格(1)/优秀/优秀 | 合格/不合格(2)/不合格(1)/合格/合格 |

一次重写只有先逐位复现被替代的工具，才谈得上可信。这些数值被写死在
`wt_smoke_test.py` 里，任何改动动了它们，测试立刻失败。

### 独立物理交叉校验

真实车次 246490 的 `CN(α)` 最小二乘斜率 **0.09873/deg**，与 `da` 文件里风洞自带的
`CNa = 0.09655` 相差 **2.26%** —— 两条完全独立的计算路径互相印证。

### 被锁死的三个已修缺陷

| 缺陷 | 甲方脚本 | 本应用 |
|---|---|---|
| 量纲 | 左右底压差停留在 MPa 与 150 比较 | 17.54 mmH2O，同量纲比较 |

```

             POST   /batches/{id}/check          执行检查
```

## 8. 配置

大模型走平台既有的 provider 无关客户端（`services/llm.py`），
在 `backend/.env` 或用户级 BYOK 设置里配置即可：

```
LLM_PROVIDER=dashscope
DEEPSEEK_API_KEY=<你的 key>            # 变量名沿用平台既有命名，值可以是任何 OpenAI 兼容服务的 key
DEEPSEEK_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
DEEPSEEK_MODEL=qwen-plus
```

**没有配置 key 时，检查、绘图、报告全部照常工作**——确定性链路完全不依赖大模型，
AI 只增强措辞、规则起草、算法生成与气动结论。质量检查不应该依赖一次网络调用。

## 9. 已知限制

- **天平载荷库**只内置了公开模板里的 `N628E`。真实天平（如 246490 用的 N636CB01）
  需要在「知识库 → 天平载荷库」补录或导入，否则超量程一项如实报未评定。
- **零飘需要连续车次**。单个车次导入时该项未评定，这是定义决定的，不是缺陷。
- **趋势判据**默认窗口 5（Nelson 规则原文是 7，但一次风洞进气常常不足 7 个车次），
  窗口可在检查配置里调整，报告会写明所用窗口与出处。
- **铰链力矩试验**（pa 中无 `L测 =`）不适用 pa 类检查，会整体标为不适用。
- 目前一次检查在请求内同步完成（5 车次约 1 秒）。车次数量上百时应改为后台任务 + 进度轮询。
