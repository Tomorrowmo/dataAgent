# 飞轮证伪实验 · 结果

> 问题：**agent 能不能从真实会话里蒸馏出你愿意留的知识？** 留存率≈0 → 飞轮没燃料。
> 燃料：`app.db` 里 10 个真实会话（从 162 条 events 压成信号）+ 8 个已存 flow_templates。
> 方法：我先当"蒸馏器"尽量多产候选，再当"严苛评审"逐条判 KEEP/DISCARD。**最终留/弃由你拍**——下面是给你勾的清单。
> 复现：`tmp/_distill_fuel.txt`（会话）、`tmp/_distill_templates.txt`（模板）。

## 头号发现（出乎意料）

**燃料存在，但它压倒性地是「产品自己反复踩的坑」，不是「领域洞见」。**

- 从 10 个会话蒸出 **~6 条高价值知识——全部是反复出现的运行时/基础设施失败模式**。
- agent 对数据下的"分析结论"（相关性、FFT 峰、数据质量）**留存率≈0**：全是**针对这份玩具数据的、不可复用的套话**。
- 8 个模板里：**4 条是真·可复用配方；3 条是从"坏会话"存下来的、把 bug 一起存进去了**（带 `voltage_v_gauss_gauss` 双滤波残渣 + 重复 interpolate）。

→ 两个直接推论：
1. **飞轮的第一桶燃料不是"专家智慧"，是"agent 自己的痛"**——该蒸馏的是**失败**（报错/重试/死循环/到步数上限/用户"没看到图"），不是成功。这正好和你的**自愈**思路合流：攒下来的就是 `known_issues` + `must_verify`。
2. **这些坑现在就在你自己 10 个会话里——根本不用上云等客户**。"部署收集洞见"那条路，这份数据又一次否掉了。

## 给这次证伪的结论

1. **飞轮有燃料 —— 证伪未通过（好事）。** 但燃料的形状不是"专家洞见"，是**「产品反复失败的模式」**。10 个会话就出了 6 条硬知识。
2. **蒸馏要瞄准失败，不是成功。** 成功会话的"分析结论"留存率≈0；失败/重试/死循环留存率高。和你的**自愈**合流。
3. **信任门非建不可，且已被坏模板证明。** 没门 = 沉淀垃圾。
4. **不需要上云收集就能起步。** 这 6 条今天就在你自己的 DB 里。

## 建议的下一步（按这次数据，不是按推演）

- **先把 K1/K2/K6 当 bug 修掉**（派生列持久化、生成工具 slug 注册一致、禁止静默替换列）——它们既是飞轮的第一批产物，**本身就是产品现在最痛的 3 个洞**。修这 3 个比建任何飞轮架构都更"缺了就生成"。
- **飞轮 MVP 缩到最小**：会话结束跑一个**只挖失败**的蒸馏器 → 候选进"待确认"托盘 → 你点确认 → 落进 `known_issues`。先在你自己的使用上转，别碰租户。
- **模板飞轮加一道最小门**：存模板前校验"这条流程在样例数据上能干净跑通"，跑不通不让存——直接挡掉 TPL 1/2/3 这类。
