# 改进清单代码审核反馈（第二轮）

审核日期：2026-11-09

审核对象：`pk/claude/改进清单.md`。

本次只读分析了改进清单和相关代码，没有修改代码或业务数据，没有启动应用、执行测试或迁移。以下为静态审核结论。

## 总体结论

这版比上一版完整，修正了 algorithm_id、轮次编号、实际输入和相对路径等问题。但仍有几个阻塞项，尤其是第 0 步依赖第 3 步、清理规则互相冲突，以及流程复现条件不足。建议修订后再开工。

## 1. 第 0 步无法按现在的拆分独立完成

S1 要求按运行编号取文件，但内置算法、对话、流程的运行记录到 D2 才建立。第 0 步完成时，这些结果仍然没有运行编号。

S4 又要求事件不再记录路径，如果此时没有可替代的结果编号，会直接影响预览和下载。

建议第 0 步先建立统一的文件归属和结果标识，或把最小运行记录能力提前；第 3 步再补批次、来源和展示字段。

此外，S3 仍遗漏了：

- `/api/datasets/preview-file`：同样未鉴权，能够读取数据。
- `/api/result-file` 实际在 `backend/app/main.py`，涉及文件不能只写 `api/datasets.py`。

## 2. 签名链接仍与安全验收矛盾

短时签名链接和“未登录或换账号拿不到文件”不是天然兼容的。

如果链接本身就是凭证，其他账号甚至未登录者拿到有效链接后仍可下载。需要明确选择：

- 每次下载校验登录和归属，前端用带 Bearer 的请求下载。
- 或允许持有签名链接的人在有效期内下载，并修改验收标准。

按当前验收要求，建议第一种。

## 3. 可以清空全部环境，必须作为独立部署前提确认

这是本版最大的范围变化，会删除账号、配置、算法、流程、技能、对话和数据，不只是历史分析结果。

文档里的前提不能替代各环境负责人的实际确认。已交付部署也可以清空，尤其需要逐个确认。

若有环境需要保留数据，只补回 S2、D5、F2 不够，还需要数据库迁移，包括：

- algorithm_id 从非空改为可空。
- Run 新字段。
- 提醒、延期和清理状态。
- 历史路径及消息事件兼容。

现有 base.py 的“缺字段就 ADD COLUMN”机制不能直接修改旧列的非空约束。

## 4. L2 的只保存主数据集那条链，仍然不可靠

现有流程步骤只存 action、slug、params、label，没有明确输入节点和算法版本，见 `backend/app/api/templates.py`。

多数据集分析可能存在交叉依赖：主数据集的后续结果依赖另一份数据。简单过滤掉其他数据集的步骤，会保存出缺少依赖的流程。

建议改为：只允许保存能完整确定输入依赖的单数据源链；存在跨数据集依赖或无法确定输入时，阻止直接保存并说明原因。

还需补上：

- 保存、更新、运行时的后端算法资格检查。
- 固定算法版本，不能只记录 slug。
- 明确失败后停止还是继续。
- 统一对话和模板对“报告输出是否进入下一步”的处理。

否则，换一份数据能跑通并不能证明保存正确；跑通也可能算错。

## 5. L1 的输入说明过度简化

第 k 步的输入是第 k−1 步产物，不总成立。

现有对话支持回退到之前的数据帧；模板也可能把报告作为旁路输出，下一步继续使用更早的数据。因此应记录执行时真实使用的输入，不能事后按步骤顺序推断。

验收“结果与对话一致”也需要同一算法版本、完整参数和相同输入；输入已清理或算法具有随机性时，应明确限制。

## 6. L3 和 L4 的产品行为不一致

L3 选择简化版：在对话里放跳转卡片，到流程页运行。

L4 却要求：欢迎页选数据直接重跑。

需要明确 L4 是也跳转到流程页，还是直接在欢迎页执行，并在当前页展示、持久化结果。

否则同一个流程有两种运行体验，测试和记录来源也不好定义。跳转卡片的按钮建议叫“前往流程页运行”，与实际行为保持一致。

## 7. R2—R4 的时间规则存在冲突

| 规则 | 问题 |
|---|---|
| 从产生起 20 天到期 | 点延期 20 天后，新到期时间从何时计算？ |
| 没看过提醒最多顺延到 60 天 | 是从创建起最多 60 天，还是额外延长 60 天？ |
| 看到过提醒才删除 | 第 60 天仍没看过，到底删不删？测试清单写的是删除 |

建议明确为可执行规则，例如：默认创建后 20 天到期；未确认提醒的自动删除最迟推迟到创建后 60 天；60 天为未确认提醒的兜底期限。用户主动延期另行计算。

“看到提醒”必须有服务端确认记录；请求过提醒接口或登录过账号，不等于看到了具体文件的清理提醒。

## 8. R6 低估了清理改造范围

文档说沿用现有逻辑，改的是触发方式和提醒，这不准确。

当前 `backend/app/services/datasets.py` 的 gc_derived_datasets 按默认 120 分钟清理未保留派生数据，并删除数据库行和文件。新规则还需要：

- 到期时间、延期时间和提醒确认状态。
- 独立运行结果文件的清理。
- Run 预览的清理。
- 流程、计算书的保护引用。
- 后台任务的重启补跑及并发保护。
- 移除或统一对话、流程结束时现有的清理调用。

这已经是清理策略重构，不能只修改定时触发方式。

## 9. R5 的保护规则需要重新定义

已保存流程用到的数据，含义不清。当前流程模板主要保存算法和参数，并不绑定原始运行数据。

应区分：

- 保存为可复用流程：通常保护算法版本，不必永久保护当次所有结果。
- 保存某次运行或计算书：保护明确列出的输入、输出和必要血缘。

当前清理逻辑会保护对话的活动 pipeline head，新清单没有明确是否保留这一规则。遗漏后可能删掉下轮对话继续分析所需的数据。

超过 60 天删除的测试也要注明：不适用于已保留或受保护的数据。

## 10. 运行记录保留，不等于仍然可以复现

运行记录保留 180 天，输入输出可能在 20～60 天清理，届时记录只能用于追溯，无法保证复现。

D4 建议改为：输入和算法版本可用时允许复现；缺失时明确显示缺失原因。

清理后最好保留数据集的名称、来源和“已清理”状态，而不是直接删行，否则血缘树、运行输入关联和编号下载接口都会失去对象。

D1 还应明确：

- 批次号在并发下如何安全递增。
- 组内步骤顺序如何保存。
- 失败、取消、部分成功如何记录。
- turn_id 与 group_id 的区别。
- 来源区分入口和执行对象。
- 如何保护 Run 不随算法删除而丢失。

## 11. 验收标准需要调整

- 有密钥 30 秒内出结果，不能作为无条件验收：外部模型延迟和故障不可控。可以验收及时反馈进度，以及超时后的确定性演示入口。
- O4 应覆盖自动展开不写入手动偏好，以及移动端不遮挡对话。
- S4 应检查整个 API 返回和消息事件，路径也可能出现在错误、日志和嵌套结果中。
- 清理测试需覆盖保留、延期与后台清理同时发生，以及文件删除失败。
- 相对路径测试要覆盖读取、预览、下载、删除和清理，不能只检查数据库字段。

## 修订优先级

建议优先改四处：

1. 补齐三个文件接口及第 0 步依赖。
2. 明确清空环境的真实范围。
3. 补全流程输入和版本约束。
4. 把清理规则写成无歧义的状态与时间规则。

这些明确后，这份清单才适合拆任务实施。
