# 改进方案代码审核反馈

审核日期：2026-11-09

本次审核采用只读代码检查，没有修改代码或业务数据，没有启动应用、执行测试或迁移，避免触发初始化、自动填充或清理逻辑。本文结论属于静态代码审核，尚未经过运行时验收。

## 总体结论

整体方向合理，但清单还不能直接作为实施方案：安全修复范围有遗漏，运行记录的数据库方案存在约束冲突，“保存流程即可复现”也缺少必要条件。建议先修正以下问题，再进入开发。

## 1. 安全问题成立，但 S1 必须覆盖三个接口

| 接口 | 实际位置 | 问题 |
|---|---|---|
| `/api/datasets/export` | `backend/app/api/datasets.py:536` | 只限制上传目录，不检查用户 |
| `/api/datasets/preview-file` | `backend/app/api/datasets.py` | 同样未鉴权，可直接读取数据内容 |
| `/api/result-file` | `backend/app/main.py:232` | 同样未鉴权，返回原文件 |

原方案把 `/api/result-file` 定位到 `datasets.py:578` 不准确，那里实际是预览接口附近。

只修下载、不修预览，仍然可以越权读取数据。风险也不只涉及共用 `results/`，上传根目录下其他用户的数据文件同样在允许范围内。

S1 需要同时解决结果归属：目前内置算法结果写入共用 `results/`，且没有对应运行记录。简单加登录后，仍然没有可靠依据判断文件属于谁。第 0 步必须建立结果归属，或先把新结果隔离到用户目录，不能等第 4 步再补。旧共用结果无法可靠确认归属时，应拒绝直接访问。

预览接口可以直接使用现有 Bearer 鉴权；下载也可以通过带鉴权的 fetch 获取 Blob，不一定要签名链接。

签名链接与验收条件存在冲突：如果签名链接本身就是下载凭证，其他账号拿到链接后、原用户退出登录后，通常仍可在有效期内下载。需要明确选择“持有短时链接即可下载”，还是“每次下载都必须是当前登录的文件所有者”。按原验收要求，后者更一致，单纯签名链接不够。

## 2. 新用户引导总体成立，O2、O4 要补实现边界

O1、O3、O5、O6 方向合理。`ChatView.tsx` 中的示例入口确实受 `!hasData` 控制，账号已经有数据时入口消失。

### O2：判断有效模型配置

不能只检查当前用户是否填了密钥。`/auth/me` 的 `has_llm_key` 只反映用户级密钥，而实际模型客户端还会回退到服务器配置。否则服务器配置了模型时，前端可能错误进入无 AI 模式。

应判断有效模型配置是否存在；配置存在但调用失败时，也应提供确定性演示入口。

### 示例填充的事实修正

已确认注册和 OIDC 新用户初始化会调用示例填充。启动路径中的 `bootstrap_admin` 只在创建新管理员时填充，管理员已存在就返回，并不是每次启动给所有用户补发。原审核中“启动时补发”的描述应收窄；本次所查启动路径不足以支持“所有账号每次启动补发”的结论。

### O4：区分自动展开与手动偏好

`WorkbenchPanel.tsx` 中现有 `setWorkbenchOpen` 每次调用都会写入 localStorage。自动展开如果复用它，就会被记成用户选择，违背方案初衷。

手机端当前默认收起是为了避免覆盖对话，“第一条消息自动展开”最好保留移动端例外。

## 3. 流程方案的问题不止是漏掉画图步骤

`FlowGraph.tsx` 的 `toSteps` 确实只保留成功的 `run_tool`，画图、生成算法等步骤不会保存。

### 保存资格必须由后端校验

当前模板创建、更新接口没有检查算法是否存在、是否可访问、是否已复核。只加前端提示，可以通过其他入口绕过。保存、修改和运行都要检查。

### 明确“复核”的含义

`is_verified` 既可能来自测试通过，也可能来自用户点击保留；`confirm-generated` 的保留操作会直接设为 True。它不等于人工检查过代码。

当前阶段可以阻止保存“尚未确认保留的 AI 草稿”，但不要把已有字段解释成严格的人工审核认证。

### slug 和参数不足以重现原对话

`services/chat_agent.py` 与 `api/templates.py` 存在实际语义差异：

- 对话可在多个数据集间切换，还可能回退到之前包含所需列的数据帧。
- 模板回放只有一个起始数据集，按线性步骤传递数据。
- 模板根据输出行数判断报告是否参与后续计算，对话中的处理方式不同。
- 模板步骤失败后仍继续执行，后续步骤可能基于上一个成功结果运行。

保存预览应说明输入数据、数据依赖，以及能否等价回放。暂不支持的多数据源或回退依赖，应阻止直接固化或明确限制，不能只提示“图表不包含”。

### 算法版本必须真正绑定

当前回放按 slug 查找当前算法，即使 Run 记录了旧版本号，也不会自动执行旧代码。需要区分：

- 重跑：使用当前算法版本。
- 复现：使用当时的算法版本和输入。

L3、L4 直接调用模板接口的方案合理，但运行结果应保存成对话消息，否则刷新后卡片会消失，后续 AI 也不知道发生过这次运行。

L2 的“至少两步”建议按成功、可保存的执行步骤计数，避免“查看工具＋运行一次”也出现两步流程入口。

## 4. D1 存在数据库约束冲突

新增 slug、version 等可空字段，不能解决 `Run.algorithm_id` 必填。

当前 `Run.algorithm_id` 非空，带算法表外键；内置算法没有对应记录，因此 `/algorithms/run` 只对自定义算法真正保存 Run。

坚持“不改旧字段约束”时，可行方向是为可执行算法建立有效的算法身份记录，让内置算法运行也能填写真实 algorithm_id，不能填 0 冒充关联。另一种方案是调整约束或新增执行记录表，但需要修改“只加字段”的约定。

原判断还需纠正：成功生成并可运行的对话 AI 算法，实际上已经写入 Algorithm 表及版本历史，并非都没有算法记录。

### D1—D5 需要补充的定义

| 项目 | 建议 |
|---|---|
| 批次 | 明确批次编号、组内顺序、批次状态和并发分配规则，不能靠前端计数 |
| 来源 | 把入口和执行对象拆开；对话里运行流程同时具有两种属性 |
| 输出 | 已有 result_dataset_id，避免再增加语义相同的 output_dataset_id |
| 消息关联 | assistant 消息目前在结束时才入库，提前产生的 Run 要有回填或预分配策略 |
| 异常记录 | 失败、取消、部分成功也必须留下状态，避免只记录成功结果 |
| 历史保留 | Algorithm 删除与 Run 的级联关系，需要和保留历史的目标一起审核 |

D3 的名称建议使用原始父数据名，避免连续派生后越拼越长。批次号作为独立标识，不承担文件名职责。

D5 显示“未知（升级前）”合理，但无需批量改写所有历史数据。能从既有血缘或消息可靠确认的来源可以保留，不能确认的才显示未知。

## 5. 当前自动清理与 D4、F3 存在冲突

`services/datasets.py` 的 `gc_derived_datasets` 会删除超过默认 120 分钟、未保留且未受保护的派生数据，连数据库记录和文件一起删除。对话、流程执行后都会触发。它不检查未来新增的 Run 引用。

因此，第 3 步建立来源记录时，必须同步调整清理策略，否则“产生于”“复现”可能很快指向已删除的数据。第 4 步仅新增 tmp 清理，不能抵消原来的派生数据清理。

需要明确运行历史、输入输出分别保留多久；数据清理后是否保留运行摘要；以及如何标记“数据已清理，无法完整复现”。

## 6. F1—F3 的迁移范围比 Dataset 路径更广

当前 `_persist_dataset` 已按用户写入，主要缺少用途分层；共用 results 位于算法执行层。相对路径改造必须统一处理读取、预览、删除、垃圾清理和下载，不能只改写入函数。

迁移不能只更新 Dataset.storage_path，至少还要核对：

- Run.result_artifacts。
- 历史消息 meta.events 中的结果路径。
- 图片引用、反馈截图、技能文件等是否在迁移范围。
- 没有数据库记录的共用结果文件如何归属。

F2 应增加迁移清单、恢复机制、内容校验，以及执行期间防止新写入。SQLite 若使用 WAL，单独复制主数据库文件不一定构成一致备份。共享结果不能仅凭文件名猜用户后迁移。

## 建议修订后的执行顺序

仍可保留 0 → 1 → 2 → 3 → 4，但需要把依赖前移：

1. 第 0 步：修三个文件读取接口，同时解决新结果归属和下载鉴权语义。
2. 第 1 步：引导页、确定性示例、工作台偏好。
3. 第 2 步：双向入口；流程保存同时补后端资格检查、回放限制和版本绑定。
4. 第 3 步：先解决 Run 算法身份和批次设计，再记录三个入口；同步调整清理策略。
5. 第 4 步：在副本演练完整迁移与恢复，再安排正式环境执行。

对于原清单的四个确认事项，审核建议是：分步提交合理；无密钥用内置算法合理；AI 草稿先确认再允许存；正式迁移先在副本演练并验证恢复。这些是审核建议，不代表已经开始实施。

## 验收补充

现有 backend/tests 主要是技能样例和幻觉评测脚本，不能直接视为覆盖上述行为的后端回归测试。

后续验收除截图外，还需要专门验证跨账号读取、流程失败与版本回放、运行记录完整性、清理保护，以及迁移幂等性与恢复能力。
